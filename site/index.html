one YAML role spec → provider‑native agent config, at spawn time

You run multi-agent loops. Each worker needs its own model, tools allowlist, permission mode, MCP servers, skills, and instructions — and each provider buries those in different files with different grammars. agent-profile resolves one declarative role profile into Claude Code subagent/teammate config or Codex agent TOML the moment your orchestrator spawns a worker, and reverses it cleanly when the worker exits.

<!-- agent-profile:begin section=problem -->

Per-worker provisioning is the unglamorous gap in every agent loop

Orchestrators got good at spawning workers. Nothing got good at provisioning them.

gap/01

Claude Code teammates don't honor the config you give them. Teammate frontmatter ignores skills and mcpServers, and there's no per-teammate permissionMode at spawn (issues #23669, #24505). Your reviewer teammate gets the same blast radius as your implementer.

gap/02

Every provider speaks a different permission grammar. Bash(git diff:*) in Claude, prefix_rule(...) in Codex. Run a mixed fleet and you maintain the same role twice, by hand, and they drift.

gap/03

Config files are shared mutable state. .mcp.json, settings.local.json, ~/.codex/config.toml — files the CLIs themselves rewrite, that secrets leak into, and that nobody dares to script against. Editing them per-spawn means surgical merges and guaranteed reversal, or it means breakage.

gap/04

Nothing validates a profile against the CLI you actually have installed. Vendors ship weekly; frontmatter fields appear and vanish. You find out a field stopped being honored when a worker silently runs with the wrong permissions.

<!-- agent-profile:begin section=demo -->

Declare the role once, render it anywhere

A role profile is plain YAML. No new skills format (SKILL.md is the standard), no new MCP bundle format (server definitions keep their existing shape), secrets only by ${env:…} reference.

.agent-profile/profiles/reviewer.yaml
apiVersion: agent-profile/v1
name: reviewer
description: Read-only code reviewer for implement-review loops.
targets: [claude-subagent, claude-teammate, codex-agent]
include: [mcp-github-readonly, perms-readonly]   # reusable capability blocks

model:
  claude: claude-fable-5
  codex: gpt-5.3-codex
  effort: high
permissionMode: readonly

tools:
  allow: [Read, Grep, "Bash(git diff:*)", "Bash(git log:*)"]
  deny:  [Write, Edit]

mcpServers:
  github-readonly:
    command: github-mcp
    args: ["--readonly"]
    env: { GITHUB_TOKEN: ${env:GITHUB_PAT_RO} }   # literals fail validate

skills: [code-review]                # resolves ~/.agents/skills/<name>/SKILL.md
context: [fragments/reviewer-instructions.md]

render is dry-run by default — there is no --dry-run flag to forget. The only ways to touch disk are --out (a sandbox directory) and apply.

render · diff · doctor
$ agent-profile render --role reviewer --target claude-subagent
PLAN (dry-run — nothing written):
  create  .claude/agents/reviewer.md          (47 lines)
  skipped mcpServers: claude-subagent cannot express per-subagent MCP servers
          → use target claude-teammate, or add servers to .mcp.json yourself

$ agent-profile diff --role implementer --target codex-agent
--- ~/.codex/config.toml
+++ rendered
+[mcp_servers.github]
+command = "github-mcp"
exit code 3   # differences exist — scriptable, like git diff --exit-code

$ agent-profile doctor --role reviewer --target claude-teammate
claude --version → 3.2.0
FINDINGS
  error  F012  frontmatter field `permissionMode` not honored by claude 3.2.0
               teammate spawn — rendered via settings.local.json defaultMode instead
  warn   F031  mcp server `github-readonly`: command `github-mcp` not found on PATH
  warn   F044  env reference ${env:GITHUB_PAT_RO} is unset in current environment
  ok          skills: 2/2 resolve in ~/.agents/skills/
exit code 4

doctor validates the profile against the installed CLI version's actually-supported fields — not against documentation. It's the preflight check nobody ships.

apply is spawn-scoped by construction: --session-id is mandatory, every action is hashed and backed up, and teardown reverses it key-by-key. Your orchestrator wraps the worker lifecycle in two shell calls.

apply · teardown — the orchestrator hook
# before spawning the worker
$ agent-profile apply --role reviewer --target claude-teammate --session-id run7-reviewer --json
{"schemaVersion":1,"sessionId":"run7-reviewer","status":"applied","actions":5,
 "backupDir":".agent-profile/backups/run7-reviewer"}

# … orchestrator spawns / runs the worker in its worktree …

# after the worker exits (success OR failure — put it in a trap)
$ agent-profile teardown --session-id run7-reviewer
  restore  .mcp.json                    (removed key mcpServers.github-readonly)
  restore  .claude/settings.local.json  (removed 2 allow rules, defaultMode)
  delete   .claude/agents/reviewer.md
  unlink   .claude/skills/code-review
  remove   CLAUDE.md block session=run7-reviewer
✓ session run7-reviewer torn down, backups deleted

If a file changed underneath an active session, apply and teardown refuse with exit 3 instead of clobbering it. Files the CLIs own outright (~/.claude.json, auth.json, plugin registries, caches) are on a hardcoded never-touch denylist — no flag bypasses it.

<!-- agent-profile:begin section=targets -->

Two runtimes, deliberately

Every adapter decision is grounded in a field survey of what each CLI actually reads, rewrites, and silently ignores. Files are classified own, merge (surgical key-level edits only), or never touch.

claude-subagent / claude-teammate

Subagent: a single generated .claude/agents/<role>.md. Teammate: routes each profile section to the nearest surface Claude Code does honor — because teammate frontmatter ignores skills/mcpServers today.

  • agent file .claude/agents/<role>.md — owned, provenance header
  • .mcp.json — merge, only keys we add
  • settings.local.json — merge allow/deny/defaultMode
  • skills — symlinks into ~/.agents/skills/, never copied
  • CLAUDE.md — marked @include block, removed at teardown

Honest limitation, printed in render output: settings are project-wide, not per-teammate. Give each worker its own worktree (orchestrators already do) and project scope ≈ worker scope.

codex-agent

A generated agent TOML plus surgical merges into config Codex itself rewrites constantly — so the adapter never owns config.toml, only the exact keys it adds.

  • agent file .codex/agents/<role>.toml — owned
  • config.toml — merge [mcp_servers.*] via toml_edit, comments and formatting preserved
  • AGENTS.md — marked @include block
  • tools grammar translated Bash(git diff:*) → prefix_rule(...); untranslatable rules flagged by doctor, never dropped silently

Anything a target can't express is reported as SKIPPED with the nearest workaround named. Nothing is ever silently dropped.

<!-- agent-profile:begin section=non-goals -->

What it is deliberately not

The non-goals are load-bearing. agent-profile is a leaf utility your orchestrator calls — nothing more.

not a registry

No publish, no pull, no marketplace, no sharing hub. There's no demand evidence for one, so it doesn't exist.

not a scenario switcher

Home/office/client machine switching is cc-switch's job, and cc-switch is free and good at it. There is no persistent use mode — apply is spawn-scoped by construction.

not a platform

No server, no accounts, no telemetry, no per-seat anything. The binary makes zero network calls. No policy engine or audit trail beyond the local state ledger.

not an orchestrator

It never spawns, schedules, supervises, or monitors agents. CAO, crew-code, agent-loop, your shell script — they spawn; agent-profile provisions.

not a new format factory

SKILL.md is the skills standard; existing MCP server definitions are the MCP standard. agent-profile references both and invents neither. No Cursor adapter either — Cursor exposes no per-role spawn primitive to target.

not a business

A prior market validation said: don't build a company here. This is the sanctioned narrow OSS probe that came out of it, with falsifiable kill criteria.

// the probe, stated plainly

This project succeeds or folds on 90-day falsifiable metrics: ≥50 stars plus ≥5 non-author issues/PRs describing the spawn-time use case (or one orchestrator integration); Anthropic not closing the Agent Teams gap natively first; and ≥3 independent users of the Codex target. If the metrics fail, the code folds into an orchestrator as an internal module — the architecture is built for exactly that. Either outcome is fine. We'd rather know.

Install

A single static Rust binary. No runtime, no daemon, no config until you write a profile.

homebrew
macOS / Linux
$ brew install xiaoleiy/tap/agent-profile
cargo
anywhere rust builds
$ cargo install agent-profile
first five minutes
$ mkdir -p .agent-profile/profiles
$ $EDITOR .agent-profile/profiles/reviewer.yaml
$ agent-profile validate --role reviewer
✓ reviewer: schema OK, 2 capability blocks resolved, no secret literals
$ agent-profile render --role reviewer --target claude-subagent   # dry-run, always
